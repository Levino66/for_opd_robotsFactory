Проект «Завод роботов»: спецификация API
Версия спецификации: v1. Актуальные значения параметров каждого прогона приходят в сообщении start. Формальные схемы — в openapi.yaml.

О проекте
Цель
Разработать алгоритм управления производственной линией, который за отведённое время получает наибольшую прибыль от сборки и продажи роботов среди команд.

Описание
Команда управляет виртуальным заводом. Все команды получают одинаковый поток поставок сырья и заготовок (например, металлический лист заданного формата, элемент управления).

В распоряжении завода:

станки (в первом раунде четыре): каждый выполняет свою операцию (резка, покраска, сборка и т. п.), работает со своими видами заготовок и тратит на операцию своё время;
склад ограниченного объёма: сюда кладутся заготовки, если станки заняты; если склад переполнен, новая поставка теряется;
покупатели (в первом раунде четыре): у каждого свои предпочтения по типам роботов и своя цена. Робот, отклонённый одним покупателем, можно предложить другому.
Алгоритм решает, какие заготовки принимать, на какой станок и в каком порядке их отправлять, каких роботов собирать и кому продавать. Параметры станков, склада и покупателей публикуются в этой спецификации; желания покупателей скрыты, и узнать их можно только предложениями. Для тренировки есть открытые миры (по номеру) и локальный симулятор.

Ожидаемый результат
Алгоритм планирования производства и продаж (любой язык).
Интерфейс, показывающий в динамике загрузку станков, заполненность склада, выпуск роботов, продажи и прибыль.
API по этой спецификации: алгоритм получает событие (поставка, освобождение станка, ответ покупателя) и возвращает управляющее решение.
Собственный эмулятор поставок для тестирования.
Краткое описание стратегии.
Репозиторий с кодом и инструкцией по запуску.
Критерии приёмки
Критерий	Требование
Допустимость действий	Решения не нарушают правил: станок получает только подходящие заготовки, склад не превышает объём, робот собран из реально полученных деталей
Время	Решение на каждое событие выдаётся в пределах лимита
Устойчивость	Алгоритм работает без сбоев весь интервал моделирования
Работоспособность	API отвечает по спецификации; интерфейс отображает ход производства
Главный критерий рейтинга	Итоговая прибыль за отведённое время при одинаковом для всех потоке поставок (среднее по нескольким скрытым мирам)
Что проверяет арена
Арена автоматически моделирует завод: передаёт события, выполняет ваши команды, проверяет их допустимость, замеряет время ответа и считает прибыль. Интерфейс, собственный эмулятор, описание стратегии и честность решения оценивают преподаватели по репозиторию и на защите.

Как проходит соревнование
Общие условия турнира
Команда — до 4 человек. Каждая команда выбирает один из четырёх проектов и соревнуется с другими командами по объективному критерию; эталонного решения нет, есть только лучшее на текущий раунд.
Решения сравниваются в нескольких раундах (контрольные точки в течение семестра), финальный прогон проходит в январе. Правила могут уточняться между раундами (закрытие лазеек, усложнение задачи), но команды узнают о них до начала очередного раунда.
Решение состоит из трёх обязательных частей: собственный алгоритм, пользовательский интерфейс для демонстрации (рекомендуется веб-приложение) и API по этой спецификации, через который арена автоматически запускает соревнование. Язык и фреймворки любые, ИИ-ассистенты и любые доступные ресурсы разрешены.
Работоспособность важнее амбиций: решение, которое не запустилось в раунде, получает 0. Простой, но стабильно работающий алгоритм лучше сложного, который падает.
На каждую операцию установлен разумный лимит времени; превышение означает, что операция не засчитана.
Академическая честность: обход проверяющей системы вместо решения задачи (подмена результата, хранение исходных данных на сервере, обращение к чужому решению) ведёт к дисквалификации из раунда и снижению оценки.
Баллы турнира учитываются при итоговой защите проекта.
Путь команды
Кабинет команды. Войдите по ключу, который выдали организаторы, выберите проект и укажите адрес вашего сервиса (при необходимости токен). Арена вызывает ваш сервис сама, поэтому адрес должен быть доступен из интернета.
Проверка API. Кнопка «Проверить API» запускает короткий сценарий и показывает по каждому шагу, что ожидалось и что получено. Успешная проверка нужна для допуска в раунд.
Тренировка. Прогон на открытых мирах (по номеру) в любое время: видна прибыль, график денег по тактам, сравнение с эталонными стратегиями на том же мире, повтор и журнал; после прогона раскрываются образцы покупателей. Количество тренировочных прогонов в час ограничено.
Раунд. Организаторы запускают несколько скрытых миров, одинаковых для всех команд. Итог — средняя прибыль по мирам (раздел 6). Результаты видны вам в кабинете, общая таблица появляется после публикации организаторами.
Отладить сервис на своём компьютере можно в песочнице в браузере (страница «Песочница»): она вызывает сервис на localhost напрямую, без выкладки в сеть.

1. Что делает ваш сервис
Ваш сервис управляет виртуальным заводом: принимает заготовки, запускает станки, собирает роботов и продаёт их покупателям. Цель — максимальная прибыль за смену.

Главная сложность: требования покупателей скрыты. Узнать их можно только предложениями, на которые покупатель отвечает ценой или отказом.

2. Мир
2.1. Время
Время виртуальное, целое, измеряется в тактах (t = 0 … horizon). Арена моделирует завод, пока не закончится смена. Реальное время ограничено только на ваш ответ (eventTimeoutMs, по умолчанию 2000 мс). Скорость вашего компьютера на модель завода не влияет, а долгий ответ влияет.

События происходят в одно время в детерминированном порядке. Решения, принятые в ответ на событие, выполняются в тот же такт.

Смена длится horizon + 1 тактов: t = 0, 1, …, horizon. Внутри такта порядок такой:

завершаются операции станков (событие machine_done, результат уже лежит на складе);
приходят поставки (событие supply, по одному на каждый предмет);
если в этом такте кратном idleEvery никаких событий не было, приходит idle;
на каждое событие вы отвечаете командами, они выполняются сразу; ответы покупателей (sale_result) приходят следующими событиями этого же такта;
в конце такта со склада списывается плата за хранение.
В такте может не быть ни одного события; за всю смену их приходит около 1300.

2.2. Предметы
Любая заготовка, деталь и робот — предмет (item) с уникальным id, видом kind и свойствами props:

{ "id": "i-104", "kind": "robot", "props": { "color": "red", "handles": false } }
Виды и допустимые значения свойств приходят в start. В v1: kind ∈ {sheet, control, body, robot}; свойства робота color ∈ {red, green, blue} и handles ∈ {true, false}.

2.3. Станки
Станок выполняет одну из своих операций. Операция принимает определённые предметы, занимает станок на duration тактов и создаёт предмет-результат:

{ "id": "m-paint", "ops": [
  { "id": "paint-red", "inputs": [{ "kind": "body", "props": { "color": null } }],
    "output": { "kind": "body", "props": { "color": "red" } }, "duration": 3, "cost": 2 }
]}
Входы тратятся при запуске, результат появляется через duration тактов (событие machine_done) и кладётся на склад. Стоимость операции cost списывается при запуске.

Свойства результата: если у операции есть inherit: N, берутся свойства входа №N, поверх них накладываются output.props. Шаблон входа: значение свойства null = «не задано», "*" = «любое заданное».

Станки v1 (цепочка: резка → [ручки] → покраска → сборка):

Станок	Операция	Вход	Результат	Такты	Стоимость
m-cut	cut	sheet	body без цвета и ручек	2	1
m-handles	add-handles	body без цвета и ручек	body с ручками	2	2
m-paint	paint-red, paint-green, paint-blue	body без цвета (с ручками или без)	body нужного цвета	3	2
m-assemble	assemble	окрашенный body + control	robot со свойствами корпуса	3	3
Узкое место — покраска и сборка (3 такта на штуку): максимум около одного робота в 3 такта.

2.4. Склад
Склад хранит заготовки, промежуточные детали и готовых роботов. В v1 объём capacity = 12 штук. За каждый такт для каждого хранящегося предмета списывается плата storageFee[kind]: заготовки sheet и control — 0,1; корпус body — 0,2; робот robot — 0,5.

Предмет на станке склад не занимает и плату не несёт, но каждый работающий станок резервирует одно место под результат. Свободное место: state.storage.free = capacity − предметов на складе − работающих станков. Поэтому результат операции всегда помещается на склад.

2.5. Поставки
В заранее неизвестные вам такты приходят предметы. В v1 это листы sheet по цене 4 и элементы управления control по цене 3; каждый вид приходит с интервалом 2–4 такта (в среднем 1 штука в 3 такта). Поставка — это предложение: заготовку можно принять (accept) за price, либо пропустить. Принятая заготовка кладётся на склад; если места нет (free = 0), команда не выполняется, деньги не списываются, заготовка потеряна. Непринятая заготовка тоже потеряна.

2.6. Покупатели
В мире buyers покупателей (в v1 — 4). Их идентификаторы известны (b1…b4). Вы не знаете, что они хотят.

У каждого покупателя скрыты: образец робота (цвет и наличие ручек), максимальная цена Pmax и коэффициент f. Цена зависит от числа свойств, не совпавших с образцом (ступенчатая функция):

Расхождений с образцом	Базовая цена
0 (совпал целиком)	Pmax
1 (другой цвет или другие ручки)	Pmax × f
2 (не совпал ни цвет, ни ручки)	0: покупатель берёт только даром
К базовой цене в каждой сделке добавляется независимая случайная поправка от −2% до +2%: покупатель может заплатить чуть дороже или чуть дешевле. Поэтому две одинаковые сделки с одним покупателем дают немного разные цены.

Известна форма правила (три ступени выше, поправка до 2%), значения скрыты: образцы, Pmax (в v1 лежит в диапазоне 45…75) и f (в диапазоне 0,30…0,60). Они генерируются по номеру мира прогона, поэтому подгонка под тренировочные миры не поможет. Ни одна цена не превышает priceCeiling = 100.

Покупатели в v1: b1…b4. Образцы разных покупателей могут совпадать.

2.7. Предложение покупателю
Команда offer предлагает покупателю конкретного робота и объявляет минимальную цену minPrice (по умолчанию 0):

если цена покупателя за этого робота не ниже minPrice, сделка совершается сразу: робот уходит, вы получаете цену (она может быть равна 0, если вы не задали minPrice);
иначе покупатель отказывается, робот остаётся у вас.
За каждое предложение списывается комиссия offerFee = 1. После предложения этот покупатель не рассматривает ваши предложения buyerCooldown = 8 тактов (ответ refused с причиной cooldown, комиссия при этом списывается). Пауза начинается и после продажи, и после отказа по цене.

Из-за паузы четыре покупателя «съедают» не больше 4 роботов за 8 тактов, то есть спрос ограничен и распределять роботов нужно между покупателями.

Ответ приходит событием sale_result (в нём есть и сам предмет item, он нужен, чтобы понять, что именно продано): sold с итоговой ценой либо refused. Цену отказавшегося покупателя вы не видите, но знаете, что она ниже minPrice. Это информация, которую нужно использовать.

Как узнавать желания покупателей. Для каждой пары «покупатель × тип робота» (цвет и ручки: всего 6 типов) у вас есть неизвестная цена. Каждое предложение даёт про неё одно сведение:

продано по цене p: цена известна (с точностью до поправки ±2%), в следующий раз можно просить почти столько же;
отказ по minPrice = m: цена ниже m, значит, верхняя граница оценки опускается до m.
Предлагая с minPrice посередине между известными границами, вы за несколько предложений сужаете вилку цены вдвое каждый раз, как при угадывании числа. Предложение с minPrice = 0 продаст робота почти всегда, но по любой цене, даже нулевой: это дорогой способ «спросить», потому что покупатель после сделки на buyerCooldown тактов недоступен. Для выбора цены полезно знать форму правила: у одного покупателя три уровня цены (Pmax, Pmax × f, 0), и по одной цене на «свой» тип можно прикинуть остальные.

2.8. Утилизация
Команда discard удаляет предмет со склада бесплатно. Нужна, чтобы освободить место.

2.9. Прибыль
прибыль = Σ цен проданных роботов
        − Σ цен принятых заготовок
        − Σ cost запущенных операций
        − Σ offerFee
        − Σ storageFee (за каждый предмет на складе, каждый такт)
        − штрафы (см. раздел 5)
Деньги условные. В начале смены у завода 0; закупки не ограничены наличными, баланс может стать отрицательным. В конце смены нераспроданные предметы стоимости не имеют.

3. Протокол
Арена вызывает ваш сервис в рамках одного прогона (runId). Состояние прогона вы храните сами (например, словарь по runId).

Методы (служебные health и info описаны в разделе «Общие правила API»):

Метод	Когда	Ответ
POST /v1/runs/{runId}/start	перед первым событием	{"ok": true}
POST /v1/runs/{runId}/event	на каждое событие	{"commands": [...]}
POST /v1/runs/{runId}/finish	после последнего такта	{"ok": true}
3.1. start
Тело содержит все параметры мира, кроме скрытых:

{
  "runId": "r-2041",
  "mode": "round",
  "horizon": 600,
  "eventTimeoutMs": 2000,
  "idleEvery": 10,
  "capacity": 12,
  "storageFee": { "sheet": 0.1, "control": 0.1, "body": 0.2, "robot": 0.5 },
  "offerFee": 1,
  "buyerCooldown": 8,
  "priceCeiling": 100,
  "buyers": ["b1", "b2", "b3", "b4"],
  "attributes": { "color": ["red", "green", "blue"], "handles": [true, false] },
  "machines": [
    { "id": "m-cut", "ops": [
      { "id": "cut", "inputs": [ { "kind": "sheet" } ],
        "output": { "kind": "body", "props": { "color": null, "handles": false } }, "duration": 2, "cost": 1 } ] },
    { "id": "m-handles", "ops": [
      { "id": "add-handles", "inputs": [ { "kind": "body", "props": { "color": null, "handles": false } } ], "inherit": 0,
        "output": { "kind": "body", "props": { "handles": true } }, "duration": 2, "cost": 2 } ] },
    { "id": "m-paint", "ops": [
      { "id": "paint-red", "inputs": [ { "kind": "body", "props": { "color": null } } ], "inherit": 0,
        "output": { "kind": "body", "props": { "color": "red" } }, "duration": 3, "cost": 2 },
      { "id": "paint-green", "...": "то же с цветом green" },
      { "id": "paint-blue", "...": "то же с цветом blue" } ] },
    { "id": "m-assemble", "ops": [
      { "id": "assemble", "inputs": [ { "kind": "body", "props": { "color": "*" } }, { "kind": "control" } ], "inherit": 0,
        "output": { "kind": "robot", "props": {} }, "duration": 3, "cost": 3 } ] }
  ]
}
Как читать описание станка:

inputs — список входов по порядку: в команде start идентификаторы itemIds надо перечислить в том же порядке (для сборки сначала корпус, потом элемент управления).
В шаблоне входа значение свойства null означает «не задано», "*" — «любое заданное»; если свойство в шаблоне не упомянуто, подходит любое значение.
inherit: N — результат наследует свойства входа №N (нумерация с 0), поверх них накладываются output.props. Например, покраска красит корпус, не трогая ручки, а сборка передаёт роботу цвет и ручки корпуса.
duration — число тактов, cost — стоимость, которая списывается при запуске.
3.2. event
Тело состоит из события и снимка состояния после этого события:

{
  "seq": 17,
  "t": 130,
  "event": { "type": "supply", "item": { "id": "i-88", "kind": "sheet", "props": {} }, "price": 4 },
  "state": {
    "cash": 212.5,
    "storage": { "capacity": 12, "free": 9, "items": [ {"id":"i-70","kind":"sheet","props":{}}, {"id":"i-71","kind":"body","props":{"color":null,"handles":false}} ] },
    "machines": [ { "id": "m-cut", "busyUntil": null }, { "id": "m-paint", "busyUntil": 133 } ],
    "buyers": [ { "id": "b1", "cooldownUntil": null } ]
  },
  "report": [ { "cmd": 1, "ok": false, "reason": "storage_full" } ]
}
report — итог ваших команд из предыдущего ответа: для каждой команды её номер cmd (с 0) и ok; у отвергнутой есть reason (список причин в разделе 3.3). На первое событие report пуст.

В state: cash — деньги сейчас; storage.free — свободные места с учётом резерва под работающие станки (раздел 2.4); у станка busyUntil — такт, когда он освободится, или null, если свободен; у покупателя cooldownUntil — такт, до которого он не принимает предложений, или null, если принимает. Снимок строится после события, но до ваших команд на него.

Типы событий:

Тип	Поля	Что решить
supply	item, price	принять (accept) или пропустить
machine_done	machineId, opId, item	результат лежит на складе; запустить следующее
sale_result	buyerId, itemId, item, outcome (sold/refused), price (если продано), reason (below_min_price/cooldown)	обновить модель рынка
idle	—	вызывается раз в idleEvery тактов, если событий не было, чтобы можно было действовать без внешнего повода
3.3. Команды
В ответе {"commands": [...]} команды выполняются по порядку. Недопустимая команда пропускается, остальные выполняются.

Команда	Поля	Правило допустимости
accept	itemId	только для предмета из текущего supply; на складе есть место
start	machineId, opId, itemIds	станок свободен; предметы на складе и подходят под входы операции
offer	buyerId, itemId, minPrice?	предмет kind=robot лежит на складе; покупатель существует
discard	itemId	предмет на складе
Ответ без команд ({"commands": []}) допустим. Пример ответа на поставку заготовки, когда свободен станок резки и есть лист на складе:

{ "commands": [
  { "cmd": "accept", "itemId": "i-88" },
  { "cmd": "start", "machineId": "m-cut", "opId": "cut", "itemIds": ["i-70"] }
] }
Не более 50 команд в ответе, остальные отбрасываются. Команды выполняются по порядку и сразу, поэтому в одном ответе можно принять поставку и тут же запустить её в работу: принятая заготовка получает тот же id, что и в событии.

Причины отказа в report:

reason	Что случилось
not_offered	accept для предмета не из текущей поставки или уже принятого
storage_full	на складе нет свободных мест
unknown_machine, unknown_op	нет такого станка или операции
machine_busy	станок занят
bad_inputs	число предметов не равно числу входов, повтор предмета, предмета нет на складе или он не подходит под шаблон входа
no_such_robot	offer для предмета, которого нет на складе или который не робот
unknown_buyer	нет такого покупателя
no_such_item	discard для предмета, которого нет на складе
unknown_command	неизвестное значение cmd
Покупатель может ответить отказом (refused) на корректный offer: это не ошибка команды, а событие sale_result.

3.4. finish
Приходит итог: прибыль, число проданных роботов, число отказов. Скрытые образцы покупателей (buyers: образец, Pmax, f) вы видите только в этом сообщении после прогона в режиме practice. В зачётном режиме (round) они не раскрываются. Открытые миры для тренировки обновляются каждый раунд, и по правилам раздела 5 переносить знания между прогонами нельзя.

4. Требования к решению
Всё состояние вы храните сами. Между разными runId никаких данных о покупателях сохранять нельзя: в каждом прогоне покупатели новые.
Ответ на событие не дольше eventTimeoutMs. Превышение = пустой ответ commands = [] и запись в журнале.
Ответ идемпотентен по seq.
Работа до конца смены без падений. Если сервис недоступен до начала прогона (не отвечает health или start), события не передаются и прибыль равна 0. Если во время смены подряд больше maxTimeouts (по умолчанию 20) событий остались без корректного ответа, прогон останавливается, а засчитывается накопленная к этому моменту прибыль. Отдельного штрафа за падение нет, но потерянные события означают упущенные продажи.
5. Недопустимое поведение
Нарушение	Последствие
Недопустимая команда (станок занят, предмет не подходит, склад полон, чужой itemId)	Команда пропускается, запись в report; штраф invalidCommandFine (по умолчанию 0 в первом раунде)
Нет ответа за eventTimeoutMs / ошибка 5xx	Событие обработано пустым ответом; при maxTimeouts подряд прогон завершается досрочно
Попытка узнать скрытые параметры не через offer (обращение к арене, чтение чужих данных)	Дисквалификация из раунда
Перенос знаний о покупателях из прошлых прогонов	Не допускается; нарушение выявляется по журналу и коду
6. Как оценивается
Проверка API (mode=check): короткий сценарий на заранее известных событиях. Проверяются формат ответов, время, реакция на недопустимые данные. Успех нужен для допуска в раунд.
Тренировка (mode=practice): запуск на открытых мирах в любое время, в том числе через песочницу в браузере (раздел 7.1). Видна прибыль и прибыль эталонного решения; в finish раскрываются образцы покупателей.
Раунд (mode=round): несколько скрытых миров (в первом раунде 5), одинаковых для всех команд. Итог — средняя прибыль по мирам. Отрицательный итог считается как есть.
Журнал: после публикации раунда команда видит все события и свои ответы по каждому миру. До публикации номера миров и журнал зачётных прогонов скрыты, потому что по номеру мира воспроизводятся поставки и покупатели.
Место в рейтинге определяется средней прибылью; при равенстве выше команда с меньшим числом недопустимых команд.

Материал	Назначение
Локальный симулятор и стратегии-ориентиры	Движок по этой спецификации (Node 16+, без зависимостей) и четыре стратегии, вызываемые как функции. Запуск: node cli.mjs --seeds 20 (флаг задаёт число миров). Команда отлаживает алгоритм локально без сети
Пример сервера	HTTP-обёртка над стратегиями-ориентирами, отвечающая по этому API; удобна как образец и для проверки песочницы
Песочница в браузере	Страница «Песочница», вкладка «Завод»: смена идёт на экране, ваш сервис вызывается с localhost, видны деньги по тактам, ошибки и сравнение с эталонами (раздел 7.1)
openapi.yaml	Формальное описание схем
Ориентиры по прибыли (v1, 20 миров, среднее ± разброс по мирам):

Стратегия	Прибыль	Что делает
«Упрямая»	≈ 90 ± 3300 (нестабильно)	Делает одного робота (красный, без ручек), предлагает всем подряд с minPrice = 30
«Наивная»	≈ 1450 ± 900	Делает роботов случайных типов, продаёт любому свободному покупателю за любую цену
«Обучающаяся»	≈ 5970 ± 740	Для каждой пары (покупатель, тип робота) ведёт границы цены и уточняет их делением пополам через minPrice; делает больше тех роботов, что выгодны
«Оракул»	≈ 7740 ± 680	Знает покупателей. Это ориентир, а не доказанный максимум
Обучающаяся стратегия простая, и её можно превзойти: например, она не использует связь между ценами одного покупателя на разные типы роботов (если известна цена на «красный без ручек», остальные цены следуют из f). Если ваш результат ниже наивной стратегии, с алгоритмом что-то не так.

7.1. Как подключить сервис для проверки
Способ	Где работает сервис	Как идут вызовы	Что нужно
Песочница в браузере	На вашем компьютере (http://localhost:порт)	Движок завода работает в вашем браузере и вызывает сервис напрямую	В сервисе включить CORS: ответ на OPTIONS и заголовки Access-Control-Allow-Origin, Access-Control-Allow-Private-Network: true. Браузер может спросить разрешение на доступ к локальной сети. Chrome и Firefox разрешают HTTPS-странице обращаться к http://localhost; в Safari это может блокироваться
Тренировка в кабинете	В сети по публичному адресу	Прогон выполняет воркер арены, так же как в раунде	Работающий публичный адрес (хостинг или туннель, например cloudflared или ngrok). CORS не нужен
Первый способ нужен, чтобы отлаживаться без выкладки в сеть: код правится и сразу проверяется. Второй показывает то, что будет в раунде: настоящую задержку сети и работу на чужом сервере. Рекомендуемый путь: разработка в песочнице, перед каждой контрольной точкой проверка прогоном арены.

Важно. Зачётный раунд (mode=round) идёт только по публичному адресу. Адрес localhost арена в раунде не принимает: проверка API сообщит об этом заранее. Сервис должен быть доступен весь раунд, ориентировочно до десяти минут на команду (около 1300 событий за прогон, пять миров, до 2 секунд на ответ).

В песочнице сетевая задержка почти нулевая, а в прогоне арены она входит в лимит eventTimeoutMs: перед раундом убедитесь, что запас по времени остаётся. Движок завода в песочнице тот же, что в арене, поэтому прибыль в том же мире совпадает.

Правила песочницы и тренировок: они не идут в рейтинг и не учитываются в баллах; нагрузка на ваш сервис такая же, как в раунде: один поток, одно событие за раз.

8. С чего начать
Поднимите сервис, который отвечает на health, start, event, finish. Минимальный пример на Node.js (принимает поставки, пока есть место, и больше ничего не делает; этого достаточно, чтобы пройти проверку API):
import http from 'node:http';
const cors = { 'access-control-allow-origin': '*', 'access-control-allow-headers': '*', 'access-control-allow-private-network': 'true' };
http.createServer((req, res) => {
  const send = (body) => { res.writeHead(200, { 'content-type': 'application/json', ...cors }); res.end(JSON.stringify(body)); };
  if (req.method === 'OPTIONS') { res.writeHead(204, cors); return res.end(); }
  if (req.url === '/v1/health') return send({ status: 'ok' });
  let raw = '';
  req.on('data', (c) => (raw += c));
  req.on('end', () => {
    if (req.url.endsWith('/event')) {
      const { event, state } = JSON.parse(raw);
      const commands = [];
      if (event.type === 'supply' && state.storage.free > 0) commands.push({ cmd: 'accept', itemId: event.item.id });
      return send({ commands });
    }
    send({ ok: true }); // start и finish
  });
}).listen(4001);
Проверьте его в песочнице в браузере (адрес http://localhost:4001) и кнопкой «Проверить API» в кабинете.
Добавьте производство: на каждое событие смотрите, какой станок свободен и что лежит на складе, и запускайте следующую операцию цепочки «резка → [ручки] → покраска → сборка».
Добавьте продажи: предлагайте роботов покупателям, у которых cooldownUntil равен null, и запоминайте результаты в sale_result.
Сравнивайте себя с эталонными стратегиями на одном и том же мире (раздел 7). Если вы ниже «Наивной», ищите ошибки в report: недопустимые команды дают больше всего потерь.
Частые ошибки: перепутанный порядок itemIds; запуск операции на предмете, который уже ушёл на другой станок в этом же ответе; забытый discard, из-за чего склад заполнен роботами, которых никто не купит; предложение покупателю, у которого ещё пауза (комиссия списывается, а продажи нет); обработка события дольше eventTimeoutMs.

9. Что может измениться в следующих раундах
Планируется: больше станков и покупателей, больше свойств робота, дороже хранение, дрейф желаний покупателей внутри смены, ограниченное число предложений. Изменения публикуются в v2 заранее.

Общие правила API
Эти правила действуют во всех проектах арены и приведены здесь полностью, отдельного общего документа нет. Арена ходит к решениям команд по одинаковым правилам, поэтому один слой арены (проверка API, журнал, лимиты, повтор) обслуживает все проекты.

Кто кого вызывает
Решение команды — HTTP-сервер по адресу, который вы указали в кабинете. Арена — клиент: ваш сервис только отвечает на запросы и сам арену не вызывает. Адрес должен быть доступен из интернета (хостинг или туннель); адреса localhost арена вызвать не может, для них есть песочница в браузере.

Служебные методы
Метод	Назначение
GET /v1/health	Ответ 200 {"status":"ok"}. Арена вызывает его в проверке API и ждёт не дольше 3 с, отвечайте быстро
GET /v1/info	Необязательно: {"name","version","project","specVersion"}
Остальные методы описаны в протоколе проекта.

Заголовки запросов арены
Заголовок	Значение
Authorization: Bearer <token>	Токен команды, если он задан в кабинете. Проверяйте его, если хотите закрыть сервер от посторонних
X-Arena-Run	Идентификатор прогона или партии
X-Arena-Spec	Версия спецификации (v1, v2…)
X-Arena-Mode	check (проверка API), practice (тренировка), round (зачётный раунд)
X-Arena-Seq	номер события в прогоне (поле seq события); для finish — следующий номер
Арена не передаёт ни в заголовках, ни в теле ничего, кроме заданий: ни скрытых миров и наборов, ни данных других команд.

Время и повторы
На событие действует лимит eventTimeoutMs (приходит в сообщении start). Нет ответа вовремя = пустой список команд, событие считается ошибкой (см. раздел 5).
Без повторов. Арена не повторяет запрос после таймаута или ошибки; поздний ответ отбрасывается.
Рекомендуется отвечать идемпотентно по X-Arena-Seq: повторный запрос с тем же номером (бывает при сетевом сбое до получения ответа) должен вернуть тот же результат.
Запросы одного прогона идут последовательно, из одного потока. Разные прогоны одной команды могут идти параллельно, но не более maxConcurrentPerTeam (настройка организатора, по умолчанию 1).
Формат ошибок
Если решение не может обработать запрос, оно отвечает кодом 4xx/5xx и телом:

{ "error": { "code": "bad_state", "message": "что случилось" } }
Арена показывает тело команде. Для «Завода» ошибка или таймаут эквивалентны пустому ответу {"commands": []}; они учитываются в счётчике ошибок (раздел 5), при превышении допустимого числа прогон останавливается.

Журнал и воспроизводимость
Арена записывает по каждому событию: что прислано, какие команды вернул сервис, отчёт о выполнении и время ответа. Команда видит журнал своего прогона и может его воспроизвести; из журнала и номера мира (хранится у арены) прогон повторяется точно.

Проверка API (check)
Кнопка «Проверить API» в кабинете запускает короткий сценарий в режиме check. Он проверяет формат ответов, время и обработку ошибочных данных, но не оценивает качество. Успешная проверка — условие допуска в раунд. В отчёте по каждому шагу видно: что ожидалось, что получено, сколько заняло. Смена из 60 тактов: все события должны получить ответ вовремя, недопустимых команд быть не должно.

Безопасность
Арена не обращается к loopback и внутренним сетям (localhost, 10.*, 192.168.*, 172.16–31.*, адреса служебных диапазонов).
Арена не следует переадресациям: ответ 3xx считается ошибкой.
Ответ на event — небольшой JSON; ответы больше 8 МБ арена обрывает.
Токен команды хранится только у арены и у команды. По возможности публикуйте сервис по HTTPS.
Версии
Версия спецификации передаётся в X-Arena-Spec и фиксируется в раунде. Новый раунд может выпустить v2; описание изменений команды получают до его начала. Решение может объявить поддерживаемые версии в GET /v1/info.
